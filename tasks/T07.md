# T07: Odzyskanie danych
## Czytaj
docs/04-data-api.md D5–D6; docs/05-acceptance.md Q2–Q3.

## Cel
Udowodnić, że teksty można odtworzyć, a błędny import ich nie niszczy.

## Wykonanie
1. Migawka przez SQLite backup do .tmp, walidacja integrity_check i zmiana nazwy.
2. Automatyczne kopie i retencja tylko udanych kopii wg D6; ręczne osobno.
3. Eksport wersjonowanego JSON oraz import preview/confirm z pełną walidacją.
Kopię wykonaj przed zatwierdzonym scaleniem, zmiany w jednej transakcji.
4. Konflikty ID: identyczne pomiń, różne grupy skopiuj z remapem zależności.
Nie zgaduj przy referencji niejednoznacznej. sourceDigest zapobiega duplikatom.
5. Narzędzie restore przy zatrzymanym serwerze, zachowanie poprzedniej bazy.
Nie pozwalaj drugiemu procesowi pisać w tej samej bazie podczas restore.
6. Sprawdź pełny cykl w nowych tmpdir, przerwanie importu, błędny plik,
nowszą wersję eksportu i brak miejsca/błąd zapisu symulowany w adapterze.

## Odbiór
- Rzeczywisty restore przywraca teksty, wersje, pomoc i relacje.
- Ponowny import tej samej kopii nie dubluje danych.
- Żaden błąd nie kończy się pustą bazą zamiast dotychczasowej.
- UI wyjaśnia, że kopia na tym samym dysku nie chroni przed awarią dysku.

## Poza tym zadaniem
Bez synchronizacji chmurowej i własnego systemu szyfrowania.

## Zamknięcie
Uaktualnij STATE.md i status w tasks/INDEX.md. Zapisz rzeczywiste komendy
i wyniki. Uruchom node scripts/check-context.mjs. Sprawdź diff przed commitem.
Jeśli kryterium wymaga niedostępnego iMaca, zapisz VERIFY_ON_MAC, nie fikcyjny sukces.
